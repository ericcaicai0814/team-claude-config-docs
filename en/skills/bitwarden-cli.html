Bitwarden CLI Patterns & Best Practices ​

Official patterns extracted from Bitwarden CLI documentation.

When to Apply ​

  • Writing scripts that interact with Bitwarden vault via bw command
  • Automating secret retrieval in CI/CD or deployment scripts
  • Managing vault items (create, edit, delete, list) programmatically
  • Setting up Bitwarden CLI authentication in automated environments
  • Working with Bitwarden Send for secure file/text sharing

Patterns ​

Pattern 1: Session Key via Environment Variable ​

Priority: HIGH

After bw unlock, export the returned session key as BW_SESSION. All subsequent bw commands will use it automatically without --session flags.

bash
# Unlock and capture session key
export BW_SESSION=$(bw unlock --passwordenv BW_PASSWORD --raw)

# Now all commands work without --session
bw list items
bw get item "my-login"

Never pass --session directly — it leaks the key into shell history.

Pattern 2: API Key Authentication for Automation ​

Priority: HIGH

For CI/CD and automated scripts, use API key environment variables to avoid interactive prompts entirely.

bash
export BW_CLIENTID="user.your-client-id"
export BW_CLIENTSECRET="your-client-secret"

bw login --apikey
# Vault is logged in but still locked — unlock next
export BW_SESSION=$(bw unlock --passwordenv BW_PASSWORD --raw)

Pattern 3: Password via Environment Variable ​

Priority: HIGH

Use --passwordenv to read the master password from an environment variable, avoiding plaintext passwords in scripts.

bash
export BW_PASSWORD="your-master-password"
bw unlock --passwordenv BW_PASSWORD

Never use --password flag directly — it appears in process listings and shell history.

Pattern 4: Template Pipeline (Create) ​

Priority: HIGH

Use the bw get template → jq → bw encode → bw create pipeline to create vault objects correctly.

bash
# Create a folder
bw get template folder | jq '.name="My Folder"' | bw encode | bw create folder

# Create a login item
bw get template item | jq "
  .name=\"GitHub Token\" |
  .login=$(bw get template item.login | jq '
    .username=\"bot@example.com\" |
    .password=\"ghp_xxxxxxxxxxxx\"
  ')
" | bw encode | bw create item

# Create item with custom field
bw get template item | jq "
  .name=\"API Key\" |
  .fields=[$(bw get template item.field | jq '.name=\"key\" | .value=\"abc123\"')]
" | bw encode | bw create item

Pattern 5: Get-Modify-Encode-Edit Pipeline (Update) ​

Priority: HIGH

To update existing objects, retrieve → modify with jq → encode → edit.

bash
# Update a password
bw get item 7ac9cae8-5067-4faf-b6ab-acfd00e2c328 \
  | jq '.login.password="newp@ssw0rd"' \
  | bw encode \
  | bw edit item 7ac9cae8-5067-4faf-b6ab-acfd00e2c328

# Update a folder name
bw get folder &lt;folder-id> \
  | jq '.name="Renamed Folder"' \
  | bw encode \
  | bw edit folder &lt;folder-id>

Pattern 6: Filtered Listing ​

Priority: MEDIUM

Use --search, --folderid, --collectionid, and --url filters to narrow bw list results.

bash
# Search by name in a specific folder
bw list items --search github --folderid 9742101e-68b8-4a07-b5b1-9578b5f88e6f

# Find items not in any folder or collection
bw list items --folderid null --collectionid null

# Search by URL
bw list items --url https://github.com

Pattern 7: Quick Secret Retrieval ​

Priority: MEDIUM

Use bw get with specific field subcommands for one-liner secret retrieval in scripts.

bash
# Get just the password
bw get password "GitHub"

# Get just the username
bw get username "GitHub"

# Get TOTP code
bw get totp "GitHub"

# Get URI
bw get uri "GitHub"

Pattern 8: Attachment Operations ​

Priority: MEDIUM

Create and retrieve attachments on vault items.

bash
# Create attachment
bw create attachment --file ./secret.pem --itemid &lt;item-id>

# Get attachment
bw get attachment &lt;attachment-id> --itemid &lt;item-id> --output ./downloaded.pem

Pattern 9: Move Item to Organization ​

Priority: MEDIUM

Use bw move (replaces deprecated bw share) to transfer items to an organization collection.

bash
echo '["&lt;collection-id>"]' | bw encode | bw move &lt;item-id> &lt;org-id>

Pattern 10: Bitwarden Send ​

Priority: MEDIUM

Create and manage ephemeral secure shares via bw send.

bash
# Create text send
bw send create --name "Shared Secret" --text "my-api-key-value"

# Edit existing send
bw send get &lt;id> | jq '.name="Updated Name" | .password=null' | bw encode | bw send edit

# Create file send
bw send create --name "Config File" --file ./config.json

Pattern 11: Organization Collection Management ​

Priority: MEDIUM

Edit organization collections via the standard get-modify-encode-edit pipeline.

bash
bw get org-collection &lt;collection-id> --organizationid &lt;org-id> \
  | jq '.name="Renamed Collection"' \
  | bw encode \
  | bw edit org-collection &lt;collection-id> --organizationid &lt;org-id>

Pattern 12: Edit Item Collections ​

Priority: MEDIUM

Assign an item to specific collections within an organization.

bash
echo '["&lt;collection-id-1>", "&lt;collection-id-2>"]' | bw encode \
  | bw edit item-collections &lt;item-id> --organizationid &lt;org-id>

Anti-Patterns ​

Hardcoding session keys in scripts ​

Session keys are sensitive decryption material. Hardcoding them means anyone with script access can decrypt your vault.

bash
# Bad — session key in plaintext
bw list items --session "5PBYGU+5yt3RHcCjoeJKx/wByU34vokGRZjXpSH7Ylo8w=="

# Good — use environment variable
export BW_SESSION=$(bw unlock --passwordenv BW_PASSWORD --raw)
bw list items

Skipping bw encode ​

The CLI requires base64-encoded JSON. Passing raw JSON will fail silently or produce errors.

bash
# Bad — raw JSON
echo '{"name":"My Folder"}' | bw create folder

# Good — always encode
echo '{"name":"My Folder"}' | bw encode | bw create folder

Leaving vault unlocked ​

An unlocked vault means the session key is still valid. Always lock when done.

bash
# Bad — script ends without locking
bw unlock --passwordenv BW_PASSWORD
bw list items
# ...script exits, vault stays unlocked

# Good — lock when done
bw unlock --passwordenv BW_PASSWORD
bw list items
bw lock

Using --password flag directly ​

The master password appears in process listings and shell history.

bash
# Bad — password visible in ps and history
bw unlock --password "MyMasterPassword123"

# Good — read from env var
export BW_PASSWORD="MyMasterPassword123"
bw unlock --passwordenv BW_PASSWORD

Not syncing before reads in long-running scripts ​

The local vault cache may be stale. Sync before critical reads.

bash
# Bad — reading potentially stale data
bw get password "Production DB"

# Good — sync first
bw sync
bw get password "Production DB"

Checklist ​

  • [ ] Session key stored in BW_SESSION env var, not hardcoded
  • [ ] API key credentials (BW_CLIENTID, BW_CLIENTSECRET) sourced from secure storage
  • [ ] Master password passed via --passwordenv, never --password
  • [ ] All JSON payloads piped through bw encode before create/edit
  • [ ] bw lock called at end of script or in trap handler
  • [ ] bw sync called before critical reads in long-running processes
  • [ ] No secrets visible in shell history or process listings
  • [ ] Self-hosted URL configured via bw config server if applicable
