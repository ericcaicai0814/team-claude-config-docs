Feature Kickoff ​

功能開發啟動流程。根據功能規模智慧選擇啟動深度，避免小功能走重流程、大功能漏步驟。

Phase 0: 規模分類 ​

收到功能需求時，先判斷規模。這一步很重要——不同規模的功能需要不同深度的準備工作。 小功能花太多時間在準備上是浪費，大功能準備不足會導致返工。

級別判斷標準範例
Light單一元件/檔案、邏輯清晰、< 2hr調整按鈕樣式、修改文案、新增一個靜態頁面
Standard2-5 個檔案、涉及既有模式、半天~1天新增一個列表頁、串接新 API、重構元件
Full跨模組、需要架構決策、> 1天新增完整功能模組、重大重構、新增認證流程

如果不確定規模，偏向選擇高一級——準備過頭比準備不足好。

各級別執行步驟 ​

步驟LightStandardFull
Phase 1: 讀取設計規範快速掃描重點閱讀完整閱讀
Phase 2: 建立 Worktree跳過建議必要
Phase 3: 拆解任務心智清單結構化清單委託 requirement-analyzer
Phase 4: 規格管理跳過視情況OpenSpec

Phase 1: 讀取設計規範 ​

在寫程式碼前，先了解設計意圖。讀什麼、讀多深取決於規模和功能類型。

Light: 快速掃描 ​

只讀與修改直接相關的檔案：

  • 該元件的 blueprint 規格（如果有）
  • docs/DESIGN_GUIDELINE.md 的相關章節

Standard: 重點閱讀 ​

根據功能類型選讀：

功能類型優先閱讀
新頁面information-architecture/routes.md → navigation.md → 相關 design-system/components/
API 串接standards/api-integration.md → standards/content-model-api-db-spec.md
UI 元件design-system/tokens/design-tokens.md → design-system/components/frontstage/
內容變更content/pages/ 相關目錄 → information-architecture/page-inventory.md

Full: 完整閱讀 ​

依序讀取：

  1. blueprint/architecture/overview.md → 技術架構總覽
  2. blueprint/init-plans/frontstage-web.md → 實作計畫（確認 Phase 和 Change 編號）
  3. blueprint/information-architecture/ → 路由、導航、使用者流程
  4. blueprint/design-system/ → 相關元件規範和 tokens
  5. blueprint/standards/ → 相關標準文件

目的：確保實作與設計規範一致，避免返工。 如果專案沒有 blueprint/ 目錄，讀取 README.md、CLAUDE.md 或其他架構文件替代。

Phase 2: 建立 Worktree 隔離開發 ​

Worktree 讓你在獨立目錄開發新功能，不影響主分支的工作狀態。 這對同時處理多個功能、或需要長時間開發的功能特別有用。

何時需要 ​

  • Light: 跳過——直接在當前分支工作即可
  • Standard: 建議——如果預期 > 3 個 commits
  • Full: 必要——隔離大型功能開發

如何建立 ​

使用 Claude Code 的 EnterWorktree 工具（輸入 "worktree" 觸發）。分支會自動命名。

如果 EnterWorktree 不可用，手動建立：

bash
git worktree add .worktrees/feature-&lt;name> -b feature/&lt;name>

規則 ​

  • 所有檔案操作使用 worktree 完整路徑
  • 完成後合併回主分支，再清理 worktree

Phase 3: 拆解任務 ​

不同規模用不同深度的拆解方式。

Light: 心智清單 ​

直接在回應中列出 2-5 個步驟，不需要正式文件：

要做的事：
1. 修改 XXX 元件的樣式
2. 確認 RWD 表現
3. 跑 lint 確認

Standard: 結構化清單 ​

用 TaskCreate 工具建立任務清單（如不可用，用 markdown checklist）：

每個任務需包含：

  • subject: 做什麼（祈使句，如「建立 NewsCard 元件」）
  • description: 完成標準和技術細節
  • activeForm: 進行式描述（如「建立 NewsCard 元件中」）
  • 標示任務間依賴關係（blockedBy）

節奏：建立全部任務 → 按序標記 in_progress → 完成 → 標記 completed → 下一個

Full: 委託 requirement-analyzer（不要自己拆解） ​

Full 級別的需求拆解必須委託 requirement-analyzer 技能處理。 這不是建議，而是流程要求。原因如下：

  • requirement-analyzer 會做多輪對話式需求釐清（Phase 1），挖掘你自己可能遺漏的邊界情境
  • 它有系統性的 Edge Cases 掃描（6 個維度：輸入、狀態、權限、網路、裝置、資料），比你手動列舉更全面
  • 它產出的功能拆解包含優先級（P0/P1/P2）和工時估算，feature-kickoff 不做這些

即使你已經對功能有充分理解，仍然要委託——因為 requirement-analyzer 的價值在於結構化的檢查流程，不是知識補充。

委託方式：

告訴用戶你需要先做需求分析，然後呼叫 requirement-analyzer 技能：

我會先用 requirement-analyzer 做完整的需求分析和任務拆解。

/requirement-analyzer

requirement-analyzer 產出後，再用 TaskCreate 將功能點（FE-001、FE-002...）轉為可追蹤的任務。

Phase 4: 規格管理（僅 Full 級別） ​

大型功能如果涉及架構決策或規格變更，用 OpenSpec 追蹤：

/opsx:new         → 建立新的 change（含 proposal）
/opsx:continue    → 逐步建立 artifacts（design → specs → tasks）
/opsx:apply       → 按 tasks 執行實作
/opsx:verify      → 驗證實作符合規格
/opsx:archive     → 完成後歸檔

判斷標準：如果功能不涉及規格或架構變更，跳過此步驟。 簡單的功能開發不需要 OpenSpec——它是為需要留下決策紀錄的重大變更設計的。

完成檢查 ​

根據級別確認：

Light ​

  • [ ] 已了解修改範圍
  • [ ] 程式碼完成
  • → 銜接 quality-gate：跑 npm run lint 和相關測試即可

Standard ​

  • [ ] 已讀取相關 blueprint 或架構文件
  • [ ] 任務已拆解並追蹤
  • [ ] Worktree 已建立（如適用）
  • → 銜接 quality-gate：完整品質閘門（build + types + lint + test）
  • → 銜接 git-workflow：按任務顆粒度 commit，完成後建 PR

Full ​

  • [ ] 已完整讀取 blueprint 相關章節
  • [ ] Worktree 已建立
  • [ ] 需求已委託 requirement-analyzer 完整分析（不是自己拆解）
  • [ ] requirement-analyzer 產出已轉為 TaskCreate 任務
  • [ ] 規格變更已用 OpenSpec 追蹤（如適用）
  • [ ] 所有任務已完成並標記 completed
  • → 銜接 quality-gate：全套檢查（build + types + lint + test + security）
  • → 銜接 git-workflow：階段性 commit + PR
  • → 銜接 doc-consistency：修改了 blueprint、IA、或架構文件時必須觸發，確保關聯文件同步

技能銜接總覽 ​

以下技能在 feature-kickoff 流程中會被用到，依時間順序：

時機技能觸發條件
Phase 3 (Full)requirement-analyzerFull 級別必須委託需求分析
Phase 4 (Full)opsx:new / opsx:continue涉及規格或架構變更時
完成後quality-gate所有級別，跑品質閘門
commit 時git-workflowStandard/Full，按顆粒度 commit
改文件時doc-consistency修改了 blueprint/IA/架構文件

注意事項 ​

  • Commit message 使用 conventional commit 前綴 + 繁體中文描述
  • 完成重要階段使用 checkpoint: 前綴提交
  • 修改 information-architecture 文件時，doc-consistency 會自動觸發同步檢查
